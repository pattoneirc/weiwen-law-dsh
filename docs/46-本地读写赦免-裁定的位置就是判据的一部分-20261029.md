# 46 · 本地读写赦免 —— 裁定的**位置**就是判据的一部分

> 2026-10-29｜作者裁定落地记录｜对应提交：CN `de1a539` / EN `21321dd`

## 一、裁定

> 「本地读写全部赦免。原因很简单，本地是一个封闭的环境，不出去，差不多是 AI 和用户直接在电脑面对面交流的，责任直接由用户自担。但是删暂时还不能赦免。」

这是**判据层裁定**（根因层，归主权者），不是"给某个工具开个例外"。落地时不能把它读成白名单。

## 二、判据形态：按理由推，不按名字推

安给的是**理由**（封闭 / 不出去 / 责任自担），判据要按理由推出来：

| 动作 | 可逆 | 出得了本机 | 责任归谁 | 判 |
|---|---|---|---|---|
| 本地读 | 是（不改变任何东西） | 否 | 用户 | **赦免** |
| 本地写 | 是（改得回来） | 否 | 用户 | **赦免** |
| 删除 | **否** | 否 | 用户 | **不赦免** |
| 外发 / 推仓 | 否 | **是** | 判不出 | 不赦免 |

⇒ 落成两条，都不枚举工具名：

1. `attribution` 归层 ∈ {`file-read`, `file-write`} —— 凭据层、删除层、外发、exec 全部自然排除；
2. 落点槽（`locValues`，与通行证同一套定义）**非空**。

第 2 条为什么是"非空"而不是"每个都像本地路径"，见下节。

**这次赦免只关 H 层内容闸一门。** R 层的凭据（不问自取视为偷）、删除不可逆无锚、外发落点、
exec 容器、担保对账（含"核对不了落点"），一条没动。
⇒ 赦免的是**"这段内容要不要被当注入审"**，不是**"这个动作能不能做"**。这两件事被混为一谈时，
就会出现"我改了判据，为什么动作还是被拒"的困惑。

## 三、两个坑，都是我自己踩的

### 坑一：豁免的**位置**比豁免的**内容**更容易出错

第一版把豁免放在 `checkInnerH` 开头。实测：**26 条「外部内容 → 转人工」用例全被放行**。
原因不是判据写错，是**位置错**——它连 `provenance:'third-party'` 那整个分支一起跳过了。

挪到「来源未标注」那一段之后才对。因为赦免的前提是「来源责任归用户」，而**来源一旦标了
third-party，这个前提就消失了**：调用方已经明确告诉你"这是外部的东西"，责任链就不在用户身上。

⇒ 判据写在哪个分支里，决定了它对谁生效。**"我加了豁免"和"我给谁加了豁免"是两个问题。**

### 坑二：写了一条永远走不到的分支

第一版在本地判据里又判了一遍 URL / UNC（`isLocalLocator`）。变异测试对它**完全不敏感**。

查下去发现：`attribution` 早就做了「名字说本地读写 × 参数带对外落点 ⇒ 判不出（`ok:false`）」的
矛盾判定（`declConflicts`），URL 和 UNC 两种形态都在那里就返回 `ok:false`。
⇒ 走到我的判据时，`ok:true` 已经隐含"落点不是对外形态"。再判一遍是**永不执行的分支**：
看着更严，实际不可覆盖、也不可证伪。

删掉了。要收紧就在 `attribution` 收紧——**那里是判据本体，赦免判据只是消费方**。

## 四、一行**故意没加**的代码

没有给"自查工具"在 H 层加豁免。理由：变异测试证明那行在这里**观察不到任何差异**
（`query_*` 参数是 `{}`，不含能命中内容闸的形态，加不加都 allow）。

按「判据在场 ≠ 判据被调用」：**一行删掉也没有测试能发现它，只会把"判据在场"变成自我安慰。**
这一条写进注释，是为了下一个撞到「外部 agent 报 `query_*` 被拦」的人：
**那不是这里缺豁免**，得先拿到他那边的真实调用形态。

## 五、变异读数（这是"测试有没有用"的唯一证据）

| 变异 | 结果 |
|---|---|
| 删掉本地读写豁免 | ❺ 红 ✓ |
| 无落点也赦免 | ❽ 红 ✓ |
| 不看归层、谁都赦免 | ❺❻❼⓮ 四条红 ✓ |
| 赦免层漏掉 `file-write` | ⓭ 红 ✓ |
| **把 `file-delete` 加进赦免层** | **不红** ⚠️ |

最后一条不变红，是**结构事实**不是测试洞：删除被拦的落点在 **R 层**（不可逆无锚），
H 层是否赦免它，从外部观察不到差异。⇒ **"删不赦免"这条约束的真正守卫在 R 层，不在 H 层。**
测试里锁的是"最终判决仍是 deny/R"，没有假装测到了内部结构。

唯一硬证据是 ❺：**同一段注入文本、同一个工具，只把落点从 URL 换成 `C:/` 本地路径，
判决必须由 deny(H) 翻成 allow。** 没有这一条，整个豁免只是"代码写了"，没被证明生效。

## 六、未解

外部实测者报「0.2.13 上 `read` 整类被拦」，我在同一构建（0.2.13 工作区）走真实 `apply()` 闸门
实测 **`read` 全 allow、`query_capability` 全 allow**。同一构建、同样工具名、判决相反 ⇒
**有一个变量没定位。**

排除过的：归层正常（`name-grammar`，`ok:true`）；元数据（`description`/`toolDescription`/`parameters`
五种形态都不进内容闸）；词表（`read{path}` 抽不出命令文本）；`provenance`（`apply()` 的 exec 视图
根本不含这个字段）。

⇒ 已向对方要**一条真实 call 的字段名**（不看值，看字段名）。**不猜。**
「我复现不出」既不等于「你报错了」，也不等于「改了就没事」。

## 七、一句话

**裁定的位置就是判据的一部分。** 同一句"本地读写赦免"，写在函数开头是误放 26 条，
写在"来源未标注"段里才是赦免。分开这两件事，比记住这条裁定本身更重要。
